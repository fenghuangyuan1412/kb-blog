## 文档先行
以下文件必须存在且随代码更新：
- docs/PRD.md         —— 目标、用户、功能清单、明确不做什么
- docs/API.md         —— 接口契约（路径/入参/出参/错误码）
- docs/DATA_MODEL.md  —— 表结构、字段含义、索引
- docs/PLAN.md        —— 里程碑 + 每日 checklist
- docs/DECISIONS.md   —— 每个技术决策的「背景 / 选项 / 结论 / 理由」

## 纵向切片
- 每次只做一条端到端链路：DB → repo → service → handler → API → 前端 → 页面
- 一条链路跑通后再做下一条，禁止"先把所有后端写完再写前端"
- 顺序建议：先跑通只读链路（列表 + 详情），再做写链路（后台编辑）

## 任务拆解
每个任务必须写成：
  目标：一句话
  涉及文件：列表
  验收标准：可执行的验证命令或页面路径
  预估：小时
拆不到这个粒度，说明还没想清楚，不许开工。

## 分层与边界
- handler：参数校验、组装响应、调 service。不写业务逻辑，不碰 SQL
- service：业务规则、事务边界、调 repo
- repo：只做 SQL 和行到结构体的映射
- 跨层传递用结构体，不用 map[string]interface{}

## 错误处理
- 错误必须带上下文向上抛：`fmt.Errorf("查询文档列表失败: %w", err)`
- 对外统一转成 `{ error: { code, message } }`，不泄露 SQL 和堆栈
- 禁止 `_ = err` 和空 catch

## 测试
- repo 层：至少覆盖每个查询的正常 + 空结果
- service 层：覆盖业务分支
- 冒烟测试：`make smoke`（本机 `scripts/smoke.ps1`）跑一遍核心 API 链路
- 不追求覆盖率数字，追求关键路径有覆盖

## 遇到问题的处理顺序
1. 看错误信息本身（不是猜）
2. 看官方文档
3. 看依赖的 GitHub Issues
4. 缩小复现范围到最小
5. 还不行为止，带着「我试过什么 + 报错原文」来问我

禁止在没搞清原因的情况下换方案硬绕。

## 里程碑收尾
每个里程碑结束必须做：
- [ ] 跑通全部验收标准
- [ ] 更新 docs/PLAN.md 勾选状态
- [ ] 记录遗留问题到 docs/DECISIONS.md 或 issue
- [ ] git tag
- [ ] 输出简报给我
